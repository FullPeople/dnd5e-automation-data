# 职业可选目录的回放归属

Web 将来源明确的可选特性目录关联到同一职业的学习进度后，旧回放程序只认识已关联的专长筛选入口，没有识别可选目录。因此职业特性目录出现一条原验证缺失；实际学习、保存、重开和旧卡保留流程仍通过，不能把验证器漏记当成功能已退步，也不能忽略这条差异直接合并。

候选只补足证据归属：特性必须是该职业在当前等级明确授予的同来源条目，原正文必须包含合法数量和同来源结构化引用的可选目录；消费者还必须声明该目录的准确别名，并确认其为已核对、只记录学习的内容选择。错误父项、来源、等级、目录位置、引用类型、执行方式、未核对规则和无关职业选择均不能算作该特性的证据。原有专长筛选检查保持。

修改前新增正例失败，修改后 29 项归属正反例通过。两份真实冻结资料的同一消费者对照中，旧程序返回无证据，新程序实际选择并保存了来源目录关联的学习项，得到 `choice:content` 回执，新增授予列表为空。这只是学习记录的可用选择，不代表整条祈唤机制已自动化。

本地完整 Data 单元为 511 项通过、11 项既有条件跳过；后者属于依赖固定 `80c94e0` 旧 Web 和原输入目录的历史 G3 对照，不将当前消费者冒充该旧基准。14 项 Node 检查、6 项 Python 检查、类型检查，以及 9 组真实消费者正反例通过；四个工作线程的准确可选目录回执与串行一致，中断后续跑回执也与串行一致。以上仍不能代替最终固定生产提交的完整真实回放。

验证生产代码改变后，须重新固定生产提交、核对消费者的全部绑定文件，再完成同一批 229 份输入、18,789 条记录的完整真实回放及配对账本。旧生产代码的回执另存，不改写绑定或混入新回放。不会放宽来源校验、前置条件或已核对标记，也不把条件跳过的 CI 当完整流水线成功。公开仓库仅保留原创测试、代码和来源元数据；真实资料正文、玩家信息和逐条私有日志不入库。尚未合并或部署。
