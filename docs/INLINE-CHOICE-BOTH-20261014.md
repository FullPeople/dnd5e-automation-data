# Explicit shared-edition metadata in typed inline choices

## Defect and expected contract

On main `efcadd83731029f5ddc802fde0a2a10c0173a407`, typed `options` nodes
accepted a reference only when either edition was absent or the two editions
were equal. Consequently a 2014 or 2024 class-feature declaration referencing
an explicitly `both` extension option was discarded as
`unresolved-inline-choice`. A shared-edition owner also discarded a declared
single-edition option. This contradicted the same producer's fixed feat and
additional-spell reference behavior.

The fixed sources for this expectation are the existing Data API contract:

- [Protocol](https://github.com/FullPeople/dnd5e-automation-data/blob/efcadd83731029f5ddc802fde0a2a10c0173a407/docs/PROTOCOL.md)
  defines `both` for eligible extension content and keeps opposing single
  editions separate.
- [Material interface](https://github.com/FullPeople/dnd5e-automation-data/blob/efcadd83731029f5ddc802fde0a2a10c0173a407/src/derive/catalogue.ts)
  carries the declared `Edition` to the structured producer.
- [Fixed feat references](https://github.com/FullPeople/dnd5e-automation-data/blob/efcadd83731029f5ddc802fde0a2a10c0173a407/src/derive/structured/classes.ts)
  and [additional-spell references](https://github.com/FullPeople/dnd5e-automation-data/blob/efcadd83731029f5ddc802fde0a2a10c0173a407/src/derive/structured/spells.ts)
  already treat explicit shared-edition metadata as compatible with a single
  edition. An existing structured regression exercises that behavior for spells.
- The public validator treats shared extension metadata consistently while
  retaining its core-book edition/source constraints.

The one-line predicate change gives typed inline references that same
interpretation. All nine pairs of `2014`, `2024` and `both` are tested: the two
opposing single-edition pairs remain rejected. One incompatible option still
rejects a whole group, even beside a shared option. Missing references remain
unresolved. Unknown-edition behavior is unchanged and no edition is assigned.

This consumes `Material.edition` already provided to the API. It does not label
an upstream book as shared, infer eligibility from a name, or teach the raw
snapshot materializer a new edition convention. That materializer still uses
its existing core-book and `classic`/`one` classification. No real extension
was newly reviewed or proven eligible for both editions by these fixtures.
